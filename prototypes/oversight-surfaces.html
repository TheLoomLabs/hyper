hyper — oversight surfaces

Four renderings of the same four surfaces, against one shared scenario. A, B and C are the three structurally different options that were built to force the decision; D is the answer — C's gutter with B's tables — and is what opens by default.

The scenario, held constant across all three

A procedure retire-preview-envs with three steps: probe preview URLs (read, target local), relabel their servers (mutate, target staging, no bound declared), delete preview servers older than 14 days (destroy, target staging, bound 5). The AI raised that bound from 3 to 5 in this revision. A run on Tuesday succeeded; today's run refused because the destroy selector expanded to 23 assets.

The four surfaces

  1. Definition review — authoring time, before anything runs. Includes the always-computed blast-radius summary handed over from #4.
  2. Change review — "what changed since Tuesday". Assets vs Observations diff differently; provenance is part of the answer.
  3. Refusal — the whole remediation path, since #4/ADR-0001 removed every bypass flag.
  4. JSON — not decoration: CI reads outcome as explicit state, never by parsing prose.

Variant A — Brief

The tool writes you a short report. Sentences, not tables. The surface takes a position on what matters and says it in words; structure is implied by paragraph, not by column. Reads like a well-written PR description.

1 · Definition review

$ hyper review procedures/retire-preview-envs.yaml

  retire-preview-envs                                    procedure · 3 steps · rev 4d7e118

  Probes preview URLs, relabels the servers behind them, and deletes preview
  servers older than 14 days.

  It may act on two targets: staging and local.
  It may destroy on staging, through delete_server only, at most 5 per run.
  It may mutate on staging with no bound declared — an unbounded mutate.
  Everything else is read-only.

  Nothing here reaches prod. No step binds it, and nothing reachable through
  this procedure declares it.

  Three things worth checking before you approve:

    1. Step 2 `label` declares no bound. If the selector widens, the write
       widens with it. Declare one unless unbounded is what you meant.

    2. Step 3 `retire` can only ever reach servers hyper created. Preview
       servers made by hand are invisible to it and will be left standing.

    3. This revision raised step 3's bound from 3 to 5. That is a widening
       of destroy authority and it is the reason you are reading this.

Buys you A reviewer who is not in the loop can read it cold. Editorialising means the surface can say "this widened destroy authority" instead of leaving you to spot it.
Costs you Prose is unscannable at 40 steps and ungreppable in a CI log. And the editorial voice must be right — a summary that says the wrong three things is worse than no summary.
Bets on Review being a human act of reading, not scanning.

4 · JSON

Table-shaped, so NDJSON: one row per line, one object per row, a type discriminator on each. hyper diff --json | jq 'select(.type=="tomb")' works without walking a tree. The final line is always the summary.

{"type":"step","index":1,"id":"probe","kind":"read","result":"completed","records":12}
{"type":"step","index":2,"id":"label","kind":"mutate","result":"completed","records":8}
{"type":"step","index":3,"id":"retire","kind":"destroy","result":"refused"}
{"type":"refusal","check":"bound_exceeded","phase":"expansion","step":3,"step_id":"retire",
 "operation":"delete_server","target":"staging","declared":5,"observed":23}
{"type":"remediation","artefact":"procedures/retire-preview-envs.yaml","line":19,
 "field":"steps[2].bound","from":5,"to":23}
{"type":"remediation","artefact":"procedures/retire-preview-envs.yaml","line":18,
 "field":"steps[2].over","hint":"narrow the selector","example_expansion":4}
{"type":"provenance","definition_revision":"4d7e118","manifest_digest":"sha256:9c1f",
 "extension_digest":null,"repo_revision":"88bc402"}
{"type":"summary","outcome":"refused","run":"01K4Z8QW6N3M2VT0BQ7YHR4C9E","records_written":0}
Buys you Scales flat. Greppable, diffable, jq-able with no tree-walking. The tool never editorialises, so it can never editorialise wrongly.
Costs you Nothing is ranked, so the one row that matters sits at the same weight as the other 39. A reviewer must already know what to look for.
Bets on Review being scanning, and the reader being the same person every time.

Variant C — Patch

One mental model for all four surfaces: the unified diff. The definition review is a diff of the artefact with blast radius in the gutter. The change review is a diff of the world. The refusal is a compiler error plus the patch that fixes it. You are always in code-review mode.

Patch-shaped, like the terminal: every surface is a list of op / path / from / to events. The same envelope carries a world diff, an artefact diff, and a refusal — one parser for all three.

    "check": "bound_exceeded", "phase": "expansion",
    "at": { "artefact": "procedures/retire-preview-envs.yaml", "line": 19, "field": "steps[2].bound" },
    "declared": 5, "observed": 23,
    "patches": [
      { "op": "replace", "path": "steps[2].bound", "from": 5, "to": 23 },
      { "op": "replace", "path": "steps[2].over", "from": "asset(label=\"preview\", age > \"14d\")",

Buys you One idiom to learn, reused four times. The remediation is literally a patch, so the fix is mechanical. Widened authority is impossible to miss — it is a + line.
Costs you A first run has no base to diff against, and a diff-native tool has to answer "what is this thing" as well as "what changed". Change review of 400 records is a very long patch.
Bets on The reader being a person who reviews code all day, and on there usually being a previous revision.

Variant D — Chosen · C's gutter with B's tables

The gutter annotates what is in this file. A table aggregates what is assembled from elsewhere. Nothing states a claim the gutter has not already marked, and the Asset / Observation / provenance split becomes three headings rather than a column.

Buys you One object under review — the artefact — with the scannability of a table over it. A summary that provably cannot contradict the source. A refusal you can act on without opening the file first.
Costs you The gutter needs a line-oriented artefact format, so it constrains the authoring-language decision. Three tables in the change review means no single chronological scan.
Bets on The reviewer reading the artefact rather than a report about it — which is what ADR-0001 already assumes, since editing that artefact is the only way past a refusal.

The five questions A/B/C were built to force — and how they landed

  1. Is the primary object of a definition review the artefact, or a table derived from it? → The artefact. The gutter is a table column embedded in the source, so it buys B's scannability without divorcing the summary from the thing under review, and it cannot lie by omission. Principle: the gutter annotates what is in this file; a table aggregates what is assembled from elsewhere. The derived step table is dead; AUTHORITY survives because it is drawn from other files.
  2. Does anything editorialise? → Only FLAGS, under a hard constraint: every flag row points at a line the gutter already marked and introduces no claim of its own. It is an index into the artefact, not an opinion about it — which makes "the summary said the wrong three things" structurally impossible rather than merely unlikely. A's prose is gone.
  3. NDJSON rows or a patch envelope? → NDJSON. Terminal tables and JSON rows map one-to-one behind a single renderer; a patch envelope is a second document shape to keep in sync by hand. It streams, too. Accepted cost: outcome is only known at the last line, so consumers tail -1 or trust the exit code — which puts more weight on codes that #13 owns.
  4. Refusal: caret excerpt, or just the remediation table? → Both. The table says where to edit; the excerpt shows the line in context, which is what lets a reader judge whether raising the bound is the right fix at all or whether the selector is the thing that's wrong. Under ADR-0001 this rendering is the entire remediation path, so it is deliberately the most verbose surface in the tool.
  5. Asset vs Observation: a column, or two tables? → Two tables. #3 made this a type split, not an attribute, and #4 hangs Expansion-reachability on it; a column value renders the most consequential fact in the diff at the same weight as a version number three columns over.

Q5 had a consequence nobody asked for: once "you did this" and "the world moved" are separate headings, provenance drift becomes the obvious third heading — "the code moved". Three actors, three tables. None of A, B or C had that; it fell out of the split.

D also fixes a factual error A and B shared: they reported records written 0 on the refused run. #4 decision 10 says no Records for the refused Step — steps 1 and 2 completed and their records are written. Only C got this right. D reports 20.

Left open, deliberately

  • Exit code numbers. #13 owns them — the mockups just say refused, and Q3 hands #13 the extra weight.
  • The authoring language. Every variant shows YAML because something had to be on the page; the fog entry says that is undecided. The gutter design assumes only that the artefact is line-oriented text.
  • Where review happens — terminal only here. Whether a definition review also renders into a GitHub PR comment is unasked.
